# رغد — خطة فريق Frontend (Frontend Team Plan)

**وثيقة عمل فريق الواجهة لتطبيق «رغد»**
مرافقة لـ `architecture.md` و`api-contract.md`

---

## 1. الغرض (Purpose)

تحدّد هذه الوثيقة عمل فريق Frontend لتطبيق «رغد»، بما يسمح بالتطوير المتوازي مع Backend مع الالتزام الصارم بالعقود المتّفق عليها. **لا تُجيز** هذه الوثيقة إنشاء endpoints أو حقول DTO أو أوسمة/أحداث جديدة أو قواعد عمل أو اعتماديات أو متغيّرات بيئة.

**مصادر الحقيقة للواجهة:**
- أشكال الاستجابة، الأخطاء، الأحداث: `new files/api-contract.md`.
- بنية النظام والوحدات: `new files/architecture.md`.
- ترتيب المراحل عبر الفرق: `new files/master-plan.md`.

---

## 2. الملكية (Ownership)

يملك فريق Frontend:

- `raghad-app/**` (React Native + Expo).
- اختبارات الواجهة، ومكوّنات UI، وإدارة الحالة المحلية.
- التكامل مع Backend عبر عميل API مركزي موثّق.

لا يعدّل فريق Frontend كود Backend أو المحركات أو المهام المجدولة إلا إذا أُوكل إليه ذلك صراحةً.

---

## 3. بيئة التشغيل الحالية (Current Runtime)

تشغيل من جذر المشروع:

```bash
npm run dev
```

- الواجهة تعمل على:
  ```text
  http://localhost:8080        (Expo Web)
  Expo Go / محاكي              (Android / iOS)
  ```
- عنوان REST للـ Backend:
  ```text
  http://localhost:3001/v1
  ```

**Assumption A1**: المنصة = React Native (Expo) تعمل على Web وAndroid وiOS.

---

## 4. قواعد Frontend (Frontend Rules)

- استخدم **عميل API مركزي**؛ لا تُنثر استدعاءات fetch الخام داخل المكوّنات.
- كل شاشة غير متزامنة يجب أن تتعامل مع حالات: **Loading / Error / Empty / Success**.
- سلوك **Responsive** إلزامي لكل ميزة مرئية (Mobile + Desktop).
- الـ mocks (إن استُخدمت) تطابق عقد الـ API تمامًا وتُوسم بوضوح كـ mocks.
- لا تخترع حقول DTO لتبسيط منطق الواجهة.
- لا تُعرّض أسرارًا في متغيّرات `EXPO_PUBLIC_*`.
- لا تستورد كود Backend.
- لا تنفّذ قواعد عمل مخفية في الواجهة؛ **Backend هو المرجع**.
- **Gamification**: عرض النقاط/السلاسل/المستويات يأتي من Backend فقط (لا احتساب محلي).

**قواعد المكوّنات والأيقونات:**
- أبقِ المكوّنات المشتركة قابلة للوصول: عناصر دلالية، دعم لوحة المفاتيح، حالات تركيز، تسميات، تباين كافٍ.
- اجعل مكوّنات UI عرضية فقط؛ لا تُضمّن منطق API أو منطق عمل.
- لا تُضِف اعتماديات أو مولّدات UI دون موافقة صريحة.

---

## 5. Mock Data وقاعدة استبدال Backend

قبل جهوزية نقاط Backend، يجوز للواجهة استخدام mocks بشرط مطابقتها `api-contract.md` تمامًا.

**قواعد الـ Mock:**
- مغلّف موحّد: `{ success, data, error, meta }`.
- بيانات النجاح تطابق شكل الاستجابة الموثّق تمامًا.
- الأخطاء تستخدم `error.code` و`error.message` و`error.fields` الموثّقة (مثل `LEVEL_LOCKED`).
- المعرّفات نصوص 24-hex.
- التواريخ ISO 8601 UTC، والأيام بتوقيت `Africa/Nouakchott`.
- النقاط/المبالغ أعداد صحيحة.
- كل قوائم العرض pagination: `page, limit, total`.
- ملفات الـ mocks تُسمّى/تُوثّق بوضوح كـ mocks.

**قاعدة الاستبدال:** كود الواجهة يستدعي طبقة adapter/عميل API؛ استبدال الـ mock بالـ Backend الحقيقي يتطلّب تغيير مصدر البيانات فقط، لا إعادة كتابة الشاشات. عند نقص حقل في العقد: **توقّف واطلب اعتماد العقد**.

## 6. بنية الواجهة (Structure)

### 6.1 التنقّل (Navigation)

**Main Tabs** (Layout رئيسي):
1. **يومي** (`/today`) — الصفحة الافتراضية.
2. **عاداتي** (`/habits`).
3. **مشاريعي** (`/projects`).
4. **الأهداف** (`/goals`).
5. **خريطة التقدم** (`/progress`).
6. **الروزنامة** (`/calendar`).
7. **الإعدادات** (`/settings`).

**Routes كاملة:**
```

/projects/:id/achievements
/goals
/goals/:id
/progress
/calendar
/notifications

/quran
/english
/brotherhood
/brotherhood/:studentId
/money
/media
```

- `MainLayout` (Tabs + Header + شريط الإشعارات).

## 7. الشاشات والمكوّنات حسب الميزة (Screens & Components)

### 7.1 المصادقة (Auth)
- **Login** (`/auth/login`): نموذج بريد + كلمة مرور، أخطاء `AUTH_REQUIRED`.
- **Profile** (`/profile`): تحديث الاسم/كلمة المرور (`PUT /users/me`).
- **تخزين التوكن**: في الذاكرة + refresh؛ لا تخزين access token في أماكن غير آمنة.

### 7.2 صفحة «يومي» (Today) — الشاشة الأهم
- رأس: التاريخ + الإحصاء (`GET /daily`): عدد العناصر، المكتمل، النقاط.
- قائمة العادات (من `GET /daily`): كل عنصر يعرض الاسم + التوقيت + زر **«تم التنفيذ»** (`POST /habit-logs`) مع تحديث متفائل (Optimistic).
- قائمة المهام (مهام المشاريع + اليدوية) مرتبة زمنيًا + زر صح (`PATCH /tasks/:id/status`).
- تعديل/حذف عناصر.
- نهاية اليوم: بطاقة المعدل + عبارة تفاعلية (`GET /daily/end-of-day`).
- مكوّنات: `HabitRow`, `TaskRow`, `DailySummaryCard`, `EndOfDayModal`.

### 7.3 عاداتي (Habits)
- قائمة العادات + زر «إضافة عادة» (`POST /habits`).
- فلاتر: النوع (يومي/موسمي)، التصنيف، الفترة، الهوايات.
- **صفحة العادة** (`/habits/:id`): رأس مشترك (أيام القيام، نسبة النجاح، نسبة الإخفاق) + تفاصيل خاصة حسب `config.special`:
  - `quran`: خطة الحفظ + `GET /habits/:id/history`.
  - `reading`: مستويات الكتب (+ عرض PDF).
  - `exercise`: زر «ابدأ» → تتبّع GPS → خريطة (خط أحمر) → كيلومترات (`POST /integrations/maps/route`).
  - `brotherhood`: قائمة الطلاب + إشعار قبل 5 د + تأجيل.
  - `family`: خطوات + قواعد التعامل.
  - `money` (`pockets`): إضافة مبلغ + ملاحظة + إحصائية.
  - `programs`: قائمة البرامج + سجل المشاهدة.
  - `beek`: Noté بمشاريع + أفكار.
  - البقية: إحصائية + ملاحظات + تاريخ (`HabitLog`).
- مكوّنات: `HabitCard`, `HabitStatsHeader`, `HabitHistoryList`, `HabitSpecial/*`.

### 7.4 مشاريعي (Projects)
- قائمة المشاريع (7) مع نسبة التقدم (`GET /projects`).
- **صفحة المشروع** (`/projects/:id`) حسب `structureType`:
  - `notes_board` (LB): ملفات + ملاحظات + لوحة مهام Trello-style (`project_nodes`).
  - `tree_cards` (Supnum): بطاقة لكل مادة → شجرة أوراق.
  - `goals_pages` (بصمة تك): أهداف → مهام + صفحات (أفكار/تسويق/إقناع).
  - `calendar_notes` (المسابقات): روزنامة قادمة/سابقة + Notes + قواعد + مهام.
  - `level_game` (رسائل من غزة / التعمق): مستويات بتاريخ ومدة + نسبة تقدم؛ التأخير = عقوبة بجمع المهام.
  - `card_sets` (الحسانية): مجموعة بطاقات (حسانية/مترجمة/Q&A/قاموس) + جلب من HF.
- روزنامة خاصة بالمشروع + صفحة إنجازات.
- مكوّنات: `ProjectCard`, `BoardView`, `TreeView`, `LevelMap`, `CardSetGrid`, `ProjectCalendar`.

### 7.5 الأهداف (Goals)
- قائمة الأهداف + نسبة التقدم عند اللمس (`GET /goals`).
- إنشاء/تعديل/حذف (`POST/PUT/DELETE /goals`).

### 7.6 خريطة التقدم (Progress Map)
- لوحة `GET /progress/overview`: تقدم المشاريع (نسبة تحقيق الأهداف) + العادات (تنفيذ يومي + نقاط).
- رسوم بيانية: خط تقدم، أعمدة، سلاسل.

### 7.7 الروزنامة (Calendar)
- عرض شهري/أسبوعي (`GET /calendar/main`)، تمييز السابق/القادم.
- إنشاء/تعديل أحداث (`POST/PUT /calendar/events`).

### 7.8 الميزات الخاصة
- **القراءة** (`/reading`): شبكة مستويات (كتاب لكل مستوى)، عرض PDF مدمج، علامة استرجاع، ملاحظات، قائمة أبجدية. القفل عبر `LEVEL_LOCKED`.
- **القرآن** (`/quran`): خطة الحفظ + `GET /quran/next` + تسجيل (`POST /quran/logs`).
- **الإنجليزية** (`/english`): 4 مهارات × مستويات، فتح تسلسلي، `POST /english/levels/:id/complete`.
- **الأخوة** (`/brotherhood`): قائمة طلاب + صفحة لكل طالب (مواد، دروس، تمارين، صور) + جلسات + تأجيل.
- **المصروف** (`/money`): إضافة مبلغ + قائمة + إحصائية إجمالي.
- **الميديا** (`/media`): برامج (سجل مشاهدة)، مذكرات، أفكار بيك.
- **الحسانية** (`/hasaniya`): جلب (`POST /hasaniya/fetch`) → تعديل → حفظ بطاقة + إحصاءات.

### 7.9 الإشعارات (Notifications)
- مركز الإشعارات (`/notifications`): قائمة + عدد غير المقروء + تعليم كمقروء (`PATCH /notifications/:id/read`, `read-all`).
- تسجيل توكن FCM (`POST /notifications/device-token`).
- استقبال إشعارات FCM in-app.

## 8. إدارة الحالة (State Management)

- **Global**: `authStore` (التوكن/المستخدم)، `settingsStore`.
- **Server State**: استخدام طبقة جلب/كاش (نمط React Query) لكل بيانات REST (اليوم، العادات، المشاريع…) مع مفاتيح استعلام ثابتة.
- **Local UI State**: `todayStore` للحالة المتفائلة في صفحة «يومي».
- لا تُخزَّن قواعد عمل في المخزن؛ المخزن يعكس ما يجلبه Backend.

### 8.1 الكاش (Caching)
- كاش موجّه بالاستعلامات مع TTL قصير (اليوم/العادات) وإبطال عند الطفرات (mutation).
- إبطال تلقائي بعد `POST /habit-logs` و`PATCH /tasks/:id/status` وفتح المستويات.
- دعم عمل دون اتصال جزئي عبر تخزين محلي لصفحة «يومي» (طابور إعادة إرسال).

## 9. الحالات: Loading / Empty / Error / Success

| الحالة | المعيار |
|---|---|
| Loading | Skeleton لكل قائمة/بطاقة (لا سبينر فارغ على كامل الشاشة) |
| Empty | رسالة ودّية + إجراء (مثال: «لا عادات بعد — أضف عادة») |
| Error | رسالة حسب `error.code` + زر إعادة المحاولة |
| Success | تحديث متفائل مع تأكيد خلفي |
| Locked | عناصر مستويات مؤجّلة تعرض قفلًا بدل زر الفتح (`LEVEL_LOCKED`) |

## 10. النماذج والتحقق (Forms & Validation)

- تحقق على مستوى الواجهة مطابق لعقد الـ API (الحقول المطلوبة، الأطوال)، مع إبقاء Backend مصدر الحقيقة.
- رسائل الخطأ تُعرض تحت الحقل عند `VALIDATION_ERROR` باستخدام `error.fields`.
- نماذج رئيسية: عادة، مهمة، مشروع، هدف، حدث روزنامة، طالب، جلسة، مبلغ، بطاقة حسانية، برنامج/مذكرة.

---

## 11. الجداول والقوائم (Tables & Lists)

- قوائم موحّدة بـ pagination (`page`, `limit`, `total`).
- Pull-to-refresh + Infinite scroll على الموبايل.
- فلاتر/بحث حسب كل مورد (النوع، التصنيف، التاريخ، البحث النصي).

---

## 12. النوافذ المنبثقة (Modals)

- تأكيد الحذف، إضافة سريعة (عادة/مهمة)، تأجيل جلسة أخوة، تعديل ملاحظة، إنهاء اليوم (End of Day)، ترقية مستوى.

---

## 13. سلوك الاستجابة (Responsive / Mobile / Desktop)

- **Mobile**: Tabs سفلية، أزرار كبيرة، تفاعل لمسي، تتبّع GPS في المقدمة.
- **Desktop/PWA**: شريط جانبي، لوحات متعددة الأعمدة (لوحة المشاريع، الروزنامة).
- تصميم متحرك وجميل على غرار Duolingo (حركات دقيقة، مكافآت بصرية عند الإنجاز).

---

## 14. قابلية الوصول (Accessibility)

- عناصر دلالية + تسميات `accessibilityLabel`، تركيز واضح، تباين كافٍ، دعم قارئ الشاشة، أهداف لمس ≥ 44px، عربي RTL كامل.

## 15. المراحل التنفيذية للواجهة (Phase-by-Phase)

> متوافقة مع `backend-plan.md` و`master-plan.md`.

### Phase A — الأساس والمصادقة
- عميل API + مغلّف + معالج أخطاء + تخزين التوكن.
- شاشة الدخول + MainLayout + التنقّل + الإعدادات/الملف الشخصي.
- **لا تخزين access token في أماكن غير آمنة.**

### Phase B — العادات و«يومي»
- صفحة «يومي» (تجميع + تم التنفيذ + نهاية اليوم).
- قائمة العادات + CRUD + صفحة العادة + الرأس الإحصائي.
- الحالات Loading/Empty/Error.

### Phase C — المهام والمشاريع والأهداف
- مهام + صفحة المشاريع + بنى المشاريع حسب `structureType` + الأهداف.

### Phase D — الميزات الخاصة
- القراءة (PDF)، القرآن، الإنجليزية، الأخوة، المصروف، الميديا، الحسانية.

### Phase E — الإشعارات والروزنامة وخريطة التقدم
- مركز الإشعارات + FCM + الروزنامة + Dashboard التقدم.

### Phase F — التقسية والإنتاج
- تمرير A11y + Responsive + الأداء (lazy loading) + اتساق الحالات + بناء الإنتاج + تدقيق متغيّرات البيئة (لا أسرار).

---

## 16. تعريف الإنجاز للواجهة (Frontend Definition of Done)

- تستخدم فقط عقود API والأحداث الموثّقة.
- بيانات الـ mock (إن استُخدمت) تطابق `api-contract.md` وقابلة للاستبدال عبر عميل API.
- تتعامل مع حالات Loading/Error/Empty/Success.
- مراجعة تخطيط الموبايل.
- لا استيراد من Backend.
- لا كشف أسرار.
- `npm run lint` و`npm run typecheck` و`npm run build` تنجح.
