# رغد — سير عمل الذكاء الاصطناعي (AI Workflow)

## 1. الغرض (Purpose)

هذا هو **دليل تشغيل الوكلاء (AI Agents)** لتطبيق «رغد». سير العمل مقصود به البساطة والأمان و**Contract-First**:

```text
Orchestrator → Build → Review/Security → موافقة المستخدم / PR
```

لا يوجد وكلاء منفصلون لـFrontend وBackend في سير العمل الافتراضي.

- **Orchestrator** يقرأ الوثائق، يحدّد نطاق المهمة، ويحمي قواعد العمل وسلامة البيانات.
- **Build Agent** ينفّذ فقط العمل المعتمد والمحدّد النطاق (Backend، Frontend، Infra، أو Docs).
- **Review/Security Agent** يقوم بفحوصات للقراءة فقط قبل الدمج أو التسليم.

كل عمل يجب أن يحترم عقد الـ API وقرارات المعمارية والخطة المرحلية في `master-plan.md`.

---

## 2. أدوار الوكلاء (Agent Roles)

| الوكيل | المسؤولية |
|---|---|
| **Orchestrator** | يقرأ `master-plan.md`, `architecture.md`, `api-contract.md`. يحدّد المرحلة والنطاق والملفات المسموحة وهل يمكن المتابعة. يُصعّد الطلبات الخطِرة أو خارج النطاق. |
| **Build Agent** | ينفّذ فقط العمل المعتمد المحدّد النطاق. قد يلمس Backend أو Frontend أو Infra أو Docs. يلتزم بالعقد وقواعد المعمارية وشروط handshake للمرحلة. |
| **Review/Security Agent** | مراجعة للقراءة فقط: انحراف النطاق، توافق العقد، المصادقة/الصلاحيات، سلامة النقاط/السلاسل، قفل المستويات، محرّك التكرار، التكاملات الخارجية، وتغطية الاختبار. |

---

## 3. سير عمل Orchestrator

1. اقرأ `master-plan.md`, `architecture.md`، والقسم ذا الصلة من `api-contract.md`.
2. حدّد المرحلة الحالية (1–8) من الخطة الرئيسية.
3. صنّف المهمة:
   `auth | habit | habit_log | gamification | recurrence | task | daily | project | project_node | goal | calendar | reading | quran | english | brotherhood | money | media | hasaniya | notification | cron | progress | integration | infra | docs`
4. افحص الاعتماديات والعوائق (مثال: handshake المرحلة غير مكتمل).
5. حدّد النطاق الدقيق بالإشارة إلى endpoints محددة أو شاشات UI أو قواعد عمل.
6. اكتب قائمة الملفات المسموحة والممنوعة (مثال: لا تلمس `habit.model.ts` أثناء مهمة notification).
7. أكّد هل تغييرات الـ API أو المخطط أو الاعتماديات أو متغيّرات البيئة أو Cron مسموحة.
8. أسنِد العمل لـBuild فقط عندما يكون النطاق آمنًا وضمن المرحلة الحالية.
9. أرسل العمل الخطِر (منطق النقاط/السلاسل، قفل المستويات، محرّك التكرار، التكاملات الخارجية) إلى Review/Security قبل التسليم النهائي.
10. لخّص الملفات المتغيّرة وخطوات التحقق المطلوبة لـhandshake المرحلة.

---

## 4. قواعد Build Agent

يعمل Build على Backend أو Frontend أو Infra أو Docs، فقط داخل النطاق المعتمد من Orchestrator.

**يجب أن:**
- يقرأ `master-plan.md`, `architecture.md`, `api-contract.md`، وقائمة handshake الخاصة بالمرحلة.
- يعيد صياغة نطاق المهمة والمرحلة الحالية قبل التحرير.
- يسرد الملفات المخطّط تعديلها قبل التحرير (مثال: `src/modules/habit/habit.service.ts`, `src/screens/daily/Today.tsx`).
- يُبقي التغييرات صغيرة وقابلة للمراجعة — PR واحد = مهمة واحدة أو شريحة وحدة واحدة.
- يتبع عقد الـ API بدقة (endpoints، DTOs، أكواد الخطأ، مغلّف الاستجابة).
- يتبع قواعد عمل المعمارية بدقة (النقاط +1/−1، السلاسل، قفل المستويات، التجديد اليومي).
- يستخدم عميل API المركزي في الواجهة؛ لا استدعاءات fetch خام داخل المكوّنات.
- يُبقي منطق العمل في Services، لا في Controllers أو Routes.
- يضيف/يحدّث الاختبارات عند توفر البنية التحتية للاختبار.
- **يتوقف فورًا** إذا احتاج وحدة أو ملفًا خارج النطاق — يُصعّد لـOrchestrator.

**يجب ألا:**
- يخترع endpoints أو حقول DTO أو مُعاملات استعلام أو أكواد خطأ أو أحداث أو متغيّرات بيئة أو اعتماديات أو سكربتات أو حقول قاعدة بيانات أو قواعد عمل.
- يغيّر عقد الـ API أو المخطط أو قواعد الصلاحيات أو منطق النقاط/السلاسل أو قفل المستويات أو قواعد الإشعارات بصمت.
- يضيف أدوات أو اعتماديات أو ملفات حزم أو خطوات CI أو ملفات بيئة أو scaffolding أو إعداد مزوّد دون موافقة.
- يخلط إعادة هيكلة غير ذات صلة أو تغييرات تنسيق أو ميزات من مراحل مختلفة.
- يخزّن الملفات أو الجلسات أو الأسرار أو الحالة الدائمة على أنظمة الملفات (استخدم التخزين السحابي أو قاعدة البيانات).
- يخزّن مفتاح Hugging Face في الواجهة؛ يجب أن يمرّ الاستدعاء عبر Backend.

## 5. سير عمل Review/Security

Review/Security للقراءة فقط إلا إذا طُلب منه الإصلاح صراحةً.

**يجب أن يفحص:**
- **انحراف النطاق** — تغييرات خارج الملفات المعتمدة أو المرحلة.
- **توافق عقد الـ API** — أشكال الطلب/الاستجابة تطابق `api-contract.md`.
- **مغلّف الاستجابة الموحّد** — `{ success, data, error, meta }`.
- **المصادقة والصلاحيات** — JWT (access قصير / refresh 7 أيام)، حدود الحساب الواحد، عدم كشف بيانات.
- **منطق النقاط والسلاسل** — احتساب مرة واحدة لكل فعل، توثيق شفاف في `points_ledger`، إعادة احتساب عند الحذف.
- **محرّك التكرار** — عادات اليوم صحيحة، لا سجلات زائدة، العادات الموسمية تُفعّل في نافذتها.
- **قفل المستويات** — القراءة والإنجليزية ومشاريع المستويات ترجع `LEVEL_LOCKED` عند تجاوز الترتيب.
- **تكامل Hugging Face** — يمرّ عبر Backend، لا أسرار في الواجهة، `502` عند الفشل.
- **رفع الملفات** — عبر Cloud Storage، لا على نظام ملفات الخادم.
- **الإشعارات** — أنواعها ومحفّزاتها صحيحة، وتعليم المقروء يعمل.
- **المهام المجدولة** — idempotent، لا إشعارات مزدوجة، تحترم النوافذ الزمنية.
- **فجوات الاختبار** — نقص اختبارات التكامل للتدفقات الحرجة (عادة → نقطة → سلسلة، مهمة، قفل مستوى).

**صيغة المخرجات:**
1. النتائج أولًا مرتّبة حسب الخطورة (عالية → متوسطة → منخفضة)، مع إشارة إلى ملف/سطر.
2. أسئلة مفتوحة عند غموض النية أو نقص تفصيل في العقد.
3. ملخص المخاطر المتبقية.
4. لا تُعاد كتابة الكود إلا إذا طُلب ذلك منفصلًا.

## 6. قواعد منع الهلوسة (Anti-Hallucination Rules)

قبل استخدام أي endpoint أو حقل DTO أو كود خطأ أو قاعدة pagination أو حدث:

1. حدّده في `api-contract.md`.
2. إذا كان مفقودًا، اعتبره **غير متاح**.
3. اطلب اعتماد العقد بدل اختراعه.
4. تحقق من أن التغييرات النهائية لا تحتوي حقولًا أو سلوكيات غير موثّقة.

قبل تطبيق أي قاعدة عمل (احتساب النقاط، السلاسل، نافذة العادات الموسمية، خطة القرآن):

1. حدّدها في `architecture.md` أو `master-plan.md`.
2. إذا كانت غير واضحة، **توقف واسأل**.
3. لا تختر بين قواعد متعارضة بصمت — صعّد لـOrchestrator.

قبل إضافة أي Feature:

1. تحقق من وجودها في `cahier_charge.md`.
2. إن لم توجد، فهي غير مطلوبة — لا تُضِفها (إلا إذا كانت ضرورية تقنيًا لميزة موجودة، مع توثيق ذلك).
3. وثّق أي **Assumption** بوضوح ولا تحوّله إلى متطلب أصلي.

---

## 7. قواعد التصعيد الحرjac (Critical Escalation Rules)

توقف وصعّد فورًا عندما تلمس المهمة أو تغيّر:

- عقد الـ API أو الـ DTOs (أي endpoint أو شكل طلب/استجابة).
- مخطط قاعدة البيانات أو الفهارس أو قواعد التحقق.
- سلوك Auth/JWT/الجلسة (بما فيه تدوير refresh).
- منطق النقاط (`points.engine`) أو السلاسل (`streak.engine`) أو محرّك التكرار.
- منطق قفل المستويات (القراءة، الإنجليزية، المشاريع بمستويات).
- خطة الحفظ القرآني أو منطق الجدولة.
- تكامل Hugging Face / Maps / التخزين السحابي / FCM.
- جدولة المهام المجدولة أو idempotency.
- متغيّرات البيئة أو الأسرار أو ملفات الحزم أو الاعتماديات أو الـ scaffold.

---

## 8. قواعد حجم PR والمهمة

- PR واحد = مهمة واحدة أو شريحة وحدة من الخطة الرئيسية.
- أفصل التدفقات الحرجة (مثال: منطق النقاط في PR، واجهة النقاط في PR آخر، مع handshake).
- تغييرات العقد/المخطط تُعزل في PR خاص وتُعتمد من قائدي الفريقين.
- لا إعادة كتابة واسعة لوحدات قائمة دون طلب صريح.
- لا تغييرات تنسيق فقط مخلوطة بتغييرات منطقية.

- <المسارات>

- <المسارات>

- Keep changes minimal.

- <قائمة، تتضمن عناصر handshake>

### Review/Security Task

```md
Review this change as read-only.
Focus: scope, API contract, auth/permissions, points/streak logic, level unlocking, recurrence, external integrations, notifications, cron idempotency, test coverage.
Output: findings first by severity with file/line refs, then open questions, then residual risk summary.
```

## 10. فرض الـ Handshake للمراحل

- لا يُسند Orchestrator عملًا من المرحلة N+1 حتى تُتحقق وتُعتمد قائمة handshake للمرحلة N (كما في `master-plan.md`).
- لا ينفّذ Build endpoints أو UI لمرحلة مستقبلية إلا بموافقة صريحة كـ «spike» أو «prototype» مع خطة تراجع واضحة.

---

## 11. الإعداد الأول (MVP Installation)

للإطلاق الأول، يجوز لـOrchestrator اعتماد مهمة لمرة واحدة لـ**seed الحساب الأول**:

- سكربت يعمل مرة واحدة (يفحص وجود مستخدمين أولًا).
- تجزئة كلمة المرور بـbcrypt.
- لا يُكشف endpoint الـ seed عبر الـ API.
- يُزال أو يُعطّل بعد نجاح الـ seed.

لا يُسمح بأي «إنشاء تلقائي» آخر للمستخدمين — في MVP يوجد حساب واحد.

---

## 12. قواعد إضافية خاصة بـ«رغد»

- **محرّك التكرار مصدر واحد للتجديد**: لا منطق تكرار داخل الواجهة.
- **النقاط والسلاسل تُحسب في Backend فقط**: الواجهة تعرض فقط.
- **قفل المستويات إلزامي**: لا كشف مستوى قبل إنهاء السابق في القراءة/الإنجليزية/المشاريع بمستويات.
- **العادات الموسمية**: تُفعّل فقط ضمن النافذة المحددة (تمام الشهر أو اقترابه 3 أيام).
- **الأسرار الخارجية** (HF/Maps/FCM/Storage) تبقى في Backend.

---

## 13. التحقق والاختبار والتوثيق

- **التحقق**: بعد كل مهمة، تشغيل `npm run lint`, `npm run typecheck`, الاختبارات الموجّهة، ثم `npm run build`.
- **الاختبار**: اختبارات تكامل للتدفقات الحرجة، واختبارات توافق العقد ضد `api-contract.md`.
- **التوثيق**: أي تغيير في العقد/المخطط يُوثّق في `api-contract.md`/`architecture.md` في نفس الـ PR، مع ملاحظة handshake لـFrontend.
- **معالجة الأخطاء**: أكواد الخطأ من Appendix B، مع `EXTERNAL_SERVICE_ERROR` للخدمات الخارجية.
- **التراجع**: كل تغيير يذكر خطة تراجع؛ الترحيلات idempotent ومُختبرة على Staging.

## 14. نقاط موافقة البشر وبوابات التحقق

| البوابة | الموافقة المطلوبة |
|---|---|
| تغيير العقد/المخطط | Backend + Frontend lead |
| تغيير Auth/الصلاحيات/الأسرار | مراجعة أمنية |
| منطق النقاط/السلاسل/قفل المستويات | Review/Security |
| المهام المجدولة/idempotency | Review/Security |
| نشر الإنتاج | موافقة يدوية (حتى يثبت الاستقرار) |
| إضافة اعتماديات/أدوات/CI | موافقة صريحة |
